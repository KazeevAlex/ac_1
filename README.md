# Проект "Планировщик обратных вызовов"

Этот проект представляет собой простой, потокобезопасный и эффективный механизм планирования обратных вызовов (callback).

## Ключевые компоненты

Реализация разделена на два основных класса: `BaseCallbackSchedulerImpl` и `BaseCallbackSchedulerWorkerImpl`.

### `BaseCallbackSchedulerImpl.java`

Этот класс предоставляет публичный API для планирования обратных вызовов.

**Преимущества:**

*   **Четкое разделение ответственности:** Класс отвечает только за прием и валидацию задач, делегируя их выполнение `CallbackSchedulerWorker`. Это упрощает код и делает его более модульным.
*   **Простой и понятный API:** Предлагает простой метод `schedule(Runnable callback, Instant when)` для использования.
*   **Надежность:** Проверяет корректность аргументов (например, что время выполнения находится в будущем), что предотвращает ошибки во время выполнения.

### `BaseCallbackSchedulerWorkerImpl.java`

Это фоновый исполнитель (worker), отвечающий за выполнение обратных вызовов в назначенное время.

**Преимущества:**

*   **Потокобезопасность:** Использует `ReentrantLock` для обеспечения безопасной обработки одновременной отправки обратных вызовов из разных потоков.
*   **Эффективное ожидание:** Реализует эффективную стратегию ожидания с использованием `ReentrantLock` и `Condition`. Вместо активного ожидания (busy-waiting), поток исполнителя "засыпает" до тех пор, пока не будет отправлена новая задача или не наступит время выполнения следующего запланированного вызова. Это значительно снижает загрузку процессора.
*   **Приоритетное выполнение:** Использует `PriorityQueue` для управления запланированными задачами. Это гарантирует, что обратные вызовы всегда выполняются в хронологическом порядке их запланированного времени.
*   **Корректное завершение работы:** Поток исполнителя может быть корректно остановлен через механизм прерывания (`interrupt`), что обеспечивает правильное освобождение ресурсов.

## Плавное завершение `BaseCallbackSchedulerImpl` (`close()`)

Метод `close()` в `BaseCallbackSchedulerImpl` реализует механизм корректного завершения работы планировщика.

1.  **Остановка приема новых задач:**
    *   Первым делом, устанавливается внутренний флаг `running` в `false`. Это немедленно блокирует возможность добавления новых задач через метод `schedule()`.

2.  **Инициация отложенного завершения:**
    *   Вызывается метод `worker.awaitTermination()`. Этот вызов добавляет в очередь `worker`-а специальную задачу, которая через заданное время инициирует его принудительную остановку.
    *   Вызывающий поток блокируется на то же время, давая "льготный период" для завершения уже выполняющихся задач.

3.  **Гарантированное принудительное завершение:**
    *   После ожидания, если `worker` по какой-либо причине всё ещё не остановлен, вызывается `worker.terminateForcibly()`. Это является защитным механизмом, который гарантирует, что планировщик в конечном итоге будет остановлен.

## Логика `conditionWaitingImplementation()` в `BaseCallbackSchedulerWorkerImpl`

Метод отвечает за эффективное ожидание потока-исполнителя (worker) до тех пор, пока не появится задача в очереди или не наступит время выполнения следующей задачи. Он использует объекты `Condition` для управления ожиданием и пробуждением потока.

Логика работы метода следующая:

1.  **Ожидание появления задач в очереди:**
    *   Метод сначала входит в цикл `while (workQueue.isEmpty())`.
    *   Внутри этого цикла вызывается `workCondition.await()`. Это заставляет текущий поток (worker) перейти в состояние ожидания, освобождая блокировку `lock`.
    *   Поток будет оставаться в состоянии ожидания до тех пор, пока:
        *   Другой поток не вызовет `workCondition.signal()` или `workCondition.signalAll()` (например, когда новая задача добавляется в `workQueue` методом `submit`).
        *   Произойдет "spurious wakeup" (ложное пробуждение).
        *   Поток будет прерван (`InterruptedException`).
    *   После пробуждения поток снова проверяет условие `workQueue.isEmpty()`. Если очередь все еще пуста (например, после "spurious wakeup"), он снова переходит в состояние ожидания. Этот цикл гарантирует, что поток продолжит ждать, пока в `workQueue` действительно не появится хотя бы одна задача.

2.  **Ожидание наступления времени выполнения следующей задачи:**
    *   Как только `workQueue` перестает быть пустой (т.е. в ней есть хотя бы одна задача), метод переходит ко второму циклу: `while (isNotCallbackTime())`.
    *   Метод `isNotCallbackTime()` проверяет, наступило ли уже время выполнения для самой ранней задачи в `workQueue` (которая находится в начале `PriorityQueue`).
    *   Если `isNotCallbackTime()` возвращает `true` (т.е. время выполнения еще не наступило), поток:
        *   Получает `callbackDeadline` (запланированное время выполнения) для следующей задачи из `workQueue.peek().when()`.
        *   Вызывает `workCondition.awaitUntil(Date.from(callbackDeadline))`. Это заставляет поток ждать до указанного времени `callbackDeadline`.
        *   Поток также может проснуться раньше, если:
            *   Другой поток вызовет `workCondition.signal()` при добавлении новой задачи, которая, возможно, должна быть выполнена раньше.
            *   Произойдет "spurious wakeup".
            *   Поток будет прерван.
    *   После пробуждения поток снова проверяет условие `isNotCallbackTime()`. Если время выполнения еще не наступило, он снова переходит в состояние ожидания (возможно, с обновленным `callbackDeadline`, если была добавлена более ранняя задача). Этот цикл гарантирует, что поток не начнет обработку задачи до наступления ее запланированного времени.

**В итоге:**

Метод обеспечивает, что поток-исполнитель:
*   Не потребляет ресурсы CPU, когда нет задач для выполнения.
*   Просыпается, как только появляется новая задача.
*   Просыпается точно в срок (или раньше, если есть более приоритетная задача), когда наступает время выполнения следующей запланированной задачи.
*   Корректно обрабатывает "spurious wakeup" благодаря использованию циклов `while` для проверки условий после пробуждения.

## Обработка "spurious wakeup" в `conditionWaitingImplementation()`

Метод использует шаблон "spurious wakeup safe" для ожидания с помощью `Condition` объектов.

"Spurious wakeup" (ложное пробуждение) — это ситуация, когда поток, ожидающий на мониторе (с помощью `wait()` или `await()`), просыпается без явного вызова `notify()`/`notifyAll()` или `signal()`/`signalAll()`.

Поведение при "spurious wakeup":

1.  **Первый цикл `while (workQueue.isEmpty()) { workCondition.await(); }`**:
    *   Если поток просыпается из-за "spurious wakeup", он немедленно перепроверяет условие `workQueue.isEmpty()`.
    *   Если `workQueue` все еще пуста, поток снова войдет в состояние ожидания.
    *   Таким образом, "spurious wakeup" в этом цикле не приведет к некорректному поведению.

2.  **Второй цикл `while (isNotCallbackTime()) { ... workCondition.awaitUntil(...); }`**:
    *   Аналогично, если `workCondition.awaitUntil()` возвращает управление из-за "spurious wakeup", поток перепроверяет условие `isNotCallbackTime()`.
    *   Если время выполнения задачи еще не наступило, поток снова войдет в состояние ожидания.
    *   "Spurious wakeup" здесь также не приведет к ошибке.

**Вывод:**
Метод корректно обрабатывает "spurious wakeup" благодаря использованию `while` циклов для проверки условий ожидания. Это стандартная и рекомендуемая практика при работе с `wait()`/`notify()` и `await()`/`signal()` в Java для обеспечения надежности и корректности многопоточных программ.

## Race condition для `Thread.interrupt()` и `Thread.isInterrupted()`

В классическом понимании **опасной гонки (race condition)**, которая приводит к повреждению данных или неопределенному поведению, в этом случае **не возникнет**. Взаимодействие между `Thread.interrupt()` и `Thread.isInterrupted()` является потокобезопасным.

Однако результат вызова `isInterrupted()` будет зависеть от точного времени выполнения, что можно считать "безопасной" или "доброкачественной" гонкой.

### Объяснение

1.  **Внутренний флаг прерывания:** Каждый объект `Thread` имеет внутренний `boolean` флаг, известный как "статус прерывания" (interrupt status).
2.  **`Thread.interrupt()`:** Этот метод просто **устанавливает** этот флаг в `true`.
3.  **`Thread.isInterrupted()`:** Этот метод просто **читает** значение этого флага.

Ключевые моменты, обеспечивающие потокобезопасность:

*   **Атомарность:** В Java чтение и запись `boolean` переменных являются **атомарными** операциями. Это означает, что вы не можете прочитать "наполовину установленное" значение. Поток, вызывающий `isInterrupted()`, увидит либо `false` (старое значение), либо `true` (новое значение), но никогда не промежуточное или поврежденное состояние.
*   **Гарантии Java Memory Model (JMM):** Спецификация Java гарантирует отношение *happens-before* между вызовом `interrupt()` и последующим обнаружением этого прерывания. Это означает, что все изменения в памяти, сделанные потоком А до вызова `someThread.interrupt()`, будут видны потоку Б после того, как он обнаружит это прерывание (например, через `isInterrupted()`, возвращающий `true`). Проще говоря, JMM обеспечивает, что установка флага одним потоком будет корректно видна другому потоку.

### Зависящий от времени результат (неопасная гонка)

Хотя повреждения данных не произойдет, результат вызова `isInterrupted()` не детерминирован и зависит от того, как планировщик потоков операционной системы выполнит эти два вызова.

Поскольку "одновременный" вызов на практике означает неопределенный порядок выполнения, вы не можете заранее предсказать, вернет ли `isInterrupted()` `true` или `false`. Однако состояние потока в любом случае останется корректным.
